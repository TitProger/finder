Веб принимает заявку текстом. Классификатор выбирает категорию, живое досье отдаётся из базы, иначе заявка уходит в очередь ресерча. Telegram-бота и тарифов free/unlimited нет. Канал связи завода TELEGRAM в карточке остаётся.

## Быстрый старт

### Требования

- Node.js 24+
- PostgreSQL 17 или Docker

### Установка зависимостей

```bash
cd backend
npm ci
```

### Настройка окружения

Скопируйте `.env.example` в `.env` и настройте переменные:

```bash
cp .env.example .env
```

**Обязательные переменные для production:**

- `ADMIN_API_TOKEN` — статический токен для доступа к HTTP API админки

**База данных:**

- `PG_HOST`, `PG_PORT`, `PG_DATABASE`, `PG_USERNAME`, `PG_PASSWORD`

**Приём досье:**

- `RESEARCH_INGEST_TOKEN` — отдельный Bearer-секрет `POST /research/ingest`. Токен админки этот вход не открывает. В production обязателен.
- `RESEARCH_TRIGGER_URL` и `RESEARCH_TRIGGER_SECRET` — webhook запуска ресерча. Секрет уходит в заголовке `X-Research-Trigger-Secret`. Пустой URL не роняет процесс: заявка остаётся в `RESEARCHING`, в лог пишется предупреждение.
- `PUBLIC_BASE_URL` — база для callback `/research/ingest` в теле webhook.
- `RESEARCH_TRIGGER_MAX_ATTEMPTS` (по умолчанию 3) и `RESEARCH_TRIGGER_RETRY_DELAY_MS` (по умолчанию 250) — повторы на 5xx и сетевых ошибках. Счётчик и последняя ошибка пишутся в `research_run`.
- `RESEARCH_STALE_AFTER_MIN` (по умолчанию 60) — сколько минут без досье, после чего прогон становится `STALE`. `RESEARCH_STALE_CHECK_MIN` (по умолчанию 5, `0` выключает таймер) — как часто это проверять. Заметка менеджеру пишется в лог.

## Аутентификация и авторизация

### HTTP API

Для доступа к защищённым эндпоинтам используйте Bearer токен:

```bash
curl -H "Authorization: Bearer YOUR_ADMIN_API_TOKEN" \
  http://localhost:8080/admin/categories
```

Админские ручки принимают заголовок `Authorization: Bearer` со значением `ADMIN_API_TOKEN`. Если пользователя с ролью ADMIN ещё нет, при старте создаётся один с именем Admin.

## Категории и классификация (Stage 2-3)

### Stage 2: Справочник категорий из YAML

- **7 категорий**: одежда, авто, электроника, оборудование/запчасти, дом/косметика, стройматериалы, общее
- **Источник правды**: `backend/seeds/categories.yaml`
- **Stable code**: каждая категория и вопрос имеет уникальный `code` для идемпотентного обновления
- **Загрузка**: `npm run seed` — upsert по `code`, не удаляет категории без кода (созданные админом вручную)

Каждая категория включает:
- Базовые вопросы (материал, количество, город и т.д.)
- Пакеты вопросов (например, для спецодежды внутри одежды)
- Площадки для поиска (с ролями: завод, китайская розница, российские маркетплейсы)

### Stage 3: Умная классификация запроса

Многоступенчатая классификация с приоритетами:

1. **Точная фраза** — как раньше, приоритет максимальный
2. **Ключевые слова** — поиск слов категории внутри текста (регистронезависимый, учитывает словоформы русского языка)
   - Пример: «Нужны лабораторные халаты 1000 шт, хлопок» → Одежда
3. **LLM-классификация** (опционально) — если ключи не совпали, запрос к LLM
   - Провайдер и модель настраиваются через env
   - Порог уверенности: `LLM_CONFIDENCE_THRESHOLD` (по умолчанию 0.7)
4. **Пауза админу** — если LLM-ключа нет или уверенность низкая

**Конфигурация LLM** (опциональная):

```env
LLM_API_BASE_URL=https://api.openai.com/v1/chat/completions  # или OpenRouter, др.
LLM_API_KEY=<ваш ключ>
LLM_MODEL=gpt-4o-mini
LLM_CONFIDENCE_THRESHOLD=0.7
```

Без ключа классификатор работает на ключевых словах и паузе, LLM-шаг пропускается.

## Безопасность

- В production приложение не стартует без `ADMIN_API_TOKEN` и `RESEARCH_INGEST_TOKEN`
- Цены НИКОГДА не отправляются клиенту — только менеджеру/админу

## Архитектура

### Слои

1. **Domain** — чистая бизнес-логика, сущности, интерфейсы репозиториев
2. **Application** — сценарии использования, сервисы, порты
3. **Infrastructure** — реализации репозиториев, внешние зависимости
4. **Interfaces** — HTTP-контроллеры

### Заявка

1. Текст заявки создаёт анонимного клиента
2. Классификация по фразам категорий
3. Уверенная категория без живой карточки запускает ресерч
4. Пауза (неуверенность) не создаёт research_run
5. Админ может запустить ещё раз: `POST /admin/inquiries/{id}/rerun-research`. Новый `run_id`

### Запуск ресерча

Заявка переходит в `RESEARCHING`. В webhook уходят `inquiry_id`, `run_id`, код категории, ответы на вопросы, текст клиента, площадки категории и `ingest_url`. Цены в тело не кладутся.

- 2xx переводит прогон в `RUNNING`.
- 4xx сразу ставит `FAILED_TO_START`.
- 5xx и обрыв сети повторяются несколько раз, затем тоже `FAILED_TO_START`.
- Нет `RESEARCH_TRIGGER_URL` — прогон остаётся `PENDING`, процесс не падает.
- Прогон без досье дольше `RESEARCH_STALE_AFTER_MIN` минут помечается `STALE`. Заявка остаётся `RESEARCHING`.

### Передача менеджеру

В лог пишется заметка, когда:

- нашлась сохранённая карточка: текст заявки, категория, продавец, цена и ссылка;
- пришло досье: краткий `summary_ru`, число компаний и офферов по слоям, до трёх самых дешёвых заводских офферов (цена, ссылка, площадка), статусы площадок и пометка «частичное»;
- прогон не запустился, завис или досье пришло со статусом `failed`.

Живую карточку, закрытие и повторный запуск делает админ по HTTP. В той же заметке слои пересчитаны в рубли, «без логистики». Штуки и комплекты не усредняются вместе.

### Слои и ручная экономика

Для досье считаются мин и медиана по каждому слою (`FACTORY`, `CHINA_OPEN`, `RUSSIA_RETAIL`, `RUSSIA_WHOLESALE`) и единице. CNY и USD переводятся курсом `fx` досье. Нет курса — берутся `FX_FALLBACK_CNY_RUB` и `FX_FALLBACK_USD_RUB`, и слой помечается запасным. RUB остаётся как есть.

Менеджер вводит доставку за единицу, пошлину в процентах, прочие затраты и наценку в процентах:

- `POST /admin/inquiries/:id/economics` со статическим `ADMIN_API_TOKEN` (и `GET` той же ручки).

Себестоимость за единицу = заводской минимум в рублях + доставка + прочие + пошлина от цены товара, затем наценка на эту сумму. Рядом розница РФ той же единицы. «Выгодно», только если розница выше себестоимости. Нет розницы или нет введённых затрат — вердикта нет. `client_price` не заполняется. Клиенту эти числа не отправляются.

### Приём досье

`POST /research/ingest` с заголовком `Authorization: Bearer $RESEARCH_INGEST_TOKEN`.

Тело — JSON в snake_case: `inquiry_id`, `run_id`, `status` (`complete` | `partial` | `failed`), `category` (code категории заявки), `sites`, `companies` с `contacts`, `offers` со слоем `FACTORY` | `CHINA_OPEN` | `RUSSIA_RETAIL` | `RUSSIA_WHOLESALE`, `fx`, `summary_ru`. Лишние поля сохраняются в `research_run.raw_payload`.

- Тот же `run_id` и то же тело → `200` и `duplicate: true`, новые строки не пишутся.
- Тот же `run_id` и другое тело → `409` `RUN_ID_REUSED`.
- Оффер без `source_url` или без `quote`, и контакт без `source_url`, попадают в `discarded`. Остальное пишется.
- Компания с уже известным USCC обновляется, повтор не даёт 409.
- Успех переводит заявку в `DOSSIER_WITH_ADMIN`.
- Цены остаются в `offer` для админа и не попадают в ответ ручки. Лимит тела — 5 МБ.

### База данных

Основные таблицы:
- Пользователи и роли: `app_user`
- Категории и вопросы: `category`, `category_phrase`, `question_pack`, `category_question`, `category_site`
- Заявки: `inquiry`, `inquiry_answer`
- Каталог: `canonical_product`, `company`, `company_contact`, `storefront`, `offer`
- Рынок: `optimal_card`, `manual_economics`, `research_run`
